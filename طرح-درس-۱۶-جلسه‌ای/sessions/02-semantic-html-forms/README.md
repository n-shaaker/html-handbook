## ۰–۱۰ | شروع

بررسی سریع تکلیف جلسهٔ قبل، دو یا سه نمونه. از هر نمونه بپرسید کدام بخش معنایی است و کدام هنوز فقط یک `div` است.

## ۱۰–۳۵ | Semantic HTML

فایل: `teach/01-semantic.html`

بگویید چرا به‌جای پر کردن صفحه از `div` از عنصر معنایی استفاده می‌کنیم:

- خوانایی کد: با دیدن نام عنصر معلوم می‌شود آن بخش عنوان صفحه است، منو است یا متن اصلی، و لازم نیست از روی کلاس CSS حدس بزنید.
- دسترس‌پذیری: صفحه‌خوان با نشانه‌های اصلی صفحه (`header`، `nav`، `main` و مانند این‌ها) می‌تواند بین بخش‌ها بپرد، به‌جای آنکه همهٔ متن را از اول تا آخر خط‌به‌خط بخواند.
- معنای سند برای مرورگر و موتور جست‌وجو: این برنامه‌ها از روی نام عنصر می‌فهمند کدام قطعه محتوای اصلی است. این همان پایهٔ سئو (SEO، یعنی دیده شدن صفحه در نتیجهٔ جست‌وجو) است.

تگ‌های کلیدی:

| تگ | کاربرد |
|----|--------|
| `header` | معرفی صفحه یا یک بخش است؛ معمولاً لوگو و عنوان همان محدوده را در خود دارد. |
| `nav` | گروه پیوندهای ناوبری اصلی است، نه هر فهرستی از پیوندها. |
| `main` | محتوای اصلی و یکتای همان صفحه است و در هر صفحه فقط یک بار می‌آید. |
| `section` | چند قطعهٔ هم‌موضوع را جمع می‌کند و معمولاً عنوان دارد. |
| `article` | محتوایی است که جدا از صفحه هم معنا دارد، مثل یک پست، کارت محصول یا نظر کاربر. |
| `aside` | محتوای جانبی است، مثل نکته یا پیوند مرتبط، که بدون آن هم متن اصلی فهمیده می‌شود. |
| `footer` | اطلاعات پایانی صفحه یا یک بخش است، مثل نام صاحب اثر. |
| `time` | تاریخ یا ساعت را نگه می‌دارد. متن داخل آن برای انسان است و `datetime` همان مقدار را برای ماشین یک‌معنا می‌کند. |

اشتباه‌هایی که در بررسی کار دانشجو باید با مثال نشان دهید: `section` بدون عنوان، چون بدون عنوان معلوم نیست آن گروه دربارهٔ چیست. چند `main` در یک صفحه، که محتوای یکتا را چندپاره می‌کند. گذاشتن `nav` دور هر گروه پیوند، مثلاً نماد شبکه‌های اجتماعی در پاورقی که مسیر اصلی سایت نیستند. پیوند `#about` وقتی هیچ عنصری `id="about"` ندارد و کلیک به جایی نمی‌رسد.

## ۳۵–۵۵ | Forms

فایل: `teach/02-form-inputs.html`

- همیشه `label` را با `for` / `id` وصل کن (یا input را داخل label بگذار) — کلیک روی متن، فیلد را فعال می‌کند و screen reader نام فیلد را می‌خواند
- `name` برای ارسال داده لازم است؛ فیلد بدون `name` اصلاً ارسال نمی‌شود
- نوع کنترل را با `type` انتخاب کنید تا مرورگر صفحه‌کلید و بررسی مناسب را بیاورد: `text` برای متن کوتاه، `email` برای نشانی ایمیل، `password` برای رمز، `number` برای عدد، `tel` برای تلفن، `date` برای تاریخ، `checkbox` برای گزینهٔ مستقل، `radio` برای یک گزینه از چند گزینه، و دکمهٔ `submit` برای فرستادن فرم.
- radioهای یک گروه باید `name` یکسان داشته باشند تا فقط یکی انتخاب شود؛ گروه را با `fieldset` + `legend` نام‌گذاری کن
- اعتبارسنجی داخلی مرورگر: `required`، `minlength`، `min`/`max`، `pattern`، `type="email"`
- `autocomplete` (مثل `email`، `new-password`) پر کردن فرم را برای کاربر سریع‌تر می‌کند
- `placeholder` جایگزین `label` نیست (با تایپ کردن ناپدید می‌شود)
- برای `button` همیشه `type` را صریح بنویس (`submit` یا `button`)؛ پیش‌فرض داخل فرم `submit` است

> اعتبارسنجی مرورگر فقط برای تجربهٔ کاربری است؛ سرور همیشه باید دوباره داده را بررسی کند.

## ۵۵–۸۰ | Live Coding

## ۸۰–۱۰۵ | تمرین

دانشجو فرم «تماس با ما» بسازد. فیلدها: نام، ایمیل، موضوع با `select`، پیام با `textarea`، یک چک‌باکس با متن «یک نسخه برای من بفرست»، و دکمهٔ ارسال. هر کنترل `label` و `name` داشته باشد تا هم خوانده شود و هم در دادهٔ ارسالی بیاید.

## ۱۰۵–۱۲۰ | بررسی + جمع‌بندی

خطاهایی که باید روی کار دانشجو پیدا کنید: برچسبی که به هیچ فیلدی وصل نیست، فیلدی که `name` ندارد و بنابراین ارسال نمی‌شود، فرمی که دکمهٔ `submit` ندارد، و دکمه‌های رادیویی که `name` متفاوت دارند و به همین دلیل چندتایی با هم انتخاب می‌شوند.

## تکلیف

صفحهٔ کامل «تماس با ما» با ساختار معنایی:

1. `header` و `nav` باشد و پیوندهای منو به بخش‌های واقعی همان صفحه، با `id`، بروند.
2. `main` فرم تماس را در خود داشته باشد و یک `section` برای اطلاعات تماس، شامل نشانی و تلفن. تلفن داخل پیوند `a` با `href="tel:..."` باشد تا در گوشی شماره را برای تماس باز کند.
3. صفحه `footer` داشته باشد تا اطلاعات پایانی از فرم جدا شود.
4. دست‌کم یک فیلد `required` باشد تا خالی ارسال نشود، و یک فیلد `pattern` داشته باشد، مثلاً برای شکل شمارهٔ موبایل.
