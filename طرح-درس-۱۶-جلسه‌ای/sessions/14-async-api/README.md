# جلسه ۱۴ — Async JavaScript + API

**مدت:** ۱۲۰ دقیقه  
**هدف:** دانشجو بفهمد کار شبکه زمان‌بر است، صفحه را قفل نمی‌کند، و پاسخ سرور را با `fetch` و `async/await` به سه حالت بارگذاری، خطا و نتیجه تبدیل کند.  
**فایل‌ها:** توضیح ناهمگامی در `teach/async-notes.js`، و تمرین دریافت کاربر در `live/index.html`، `live/styles.css` و `live/app.js` با سرویس JSONPlaceholder

| زمان | کار |
|------|-----|
| ۰–۱۵ | کد همگام و ناهمگام را با یک `setTimeout` صفر مقایسه کنید تا معلوم شود خط بعدی همیشه منتظر شبکه نمی‌ماند. |
| ۱۵–۳۵ | یک Promise ساده با حالت‌های در انتظار، موفق و ناموفق بسازید و با `.then` و `.catch` نتیجه‌اش را بخوانید. |
| ۳۵–۵۵ | همان منطق را با `async/await` و `try/catch` بازنویسی کنید تا ترتیب خواندن کد از بالا به پایین شود. |
| ۵۵–۸۰ | `fetch` را به سه مرحله بشکنید: فرستادن درخواست، بررسی `response.ok`، و خواندن JSON. |
| ۸۰–۹۵ | روش‌های HTTP را با معنا بگویید: خواندن، ساختن، به‌روزرسانی و حذف، به‌همراه کدهای وضعیت پرتکرار. |
| ۹۵–۱۱۰ | نشان دهید خطای ۴۰۴ از `fetch` پرتاب نمی‌شود و باید خودتان `ok` را بسنجید، و خطای شبکه را در `catch` بگیرید. |
| ۱۱۰–۱۲۰ | دانشجو یک نشانی دیگر از همان سرویس را با سه حالت بارگذاری، خطا و نتیجهٔ خالی نشان دهد. |

سرویس دمو این نشانی است: `https://jsonplaceholder.typicode.com/users`. رایگان است و کلید API نمی‌خواهد. درخواست‌های POST و PUT و DELETE در این سرویس شبیه‌سازی می‌شوند، یعنی پاسخ موفق می‌گیرید ولی داده واقعاً روی سرور ذخیره نمی‌شود. این را بگویید تا دانشجو فکر نکند بار بعد همان کاربر را در فهرست می‌بیند.

`teach/async-notes.js` را در Console مرورگر اجرا کنید، یا با `node teach/async-notes.js` اگر Node از نسخهٔ ۱۸ به بالا باشد، چون از آن نسخه `fetch` داخل خود Node هست.

## مفاهیم کلیدی

- **همگام در برابر ناهمگام:** کد همگام خط‌به‌خط اجرا می‌شود و خط بعدی منتظر تمام شدن خط فعلی می‌ماند. کار زمان‌بر، مثل درخواست شبکه یا تایمر، ناهمگام است تا رابط کاربری قفل نشود و کاربر هنوز بتواند اسکرول کند. حتی `setTimeout(..., 0)` بعد از کد همگام همین نوبت اجرا می‌شود. این را با یک `console.log` قبل و بعد از تایمر صفر نشان دهید تا ترتیب غافلگیرکننده دیده شود.
- **Promise** وعدهٔ یک مقدار در آینده است. سه حالت دارد: `pending` یعنی هنوز معلوم نیست، `fulfilled` یعنی مقدار آماده است، و `rejected` یعنی عملیات شکست خورده. این وعده را یا با `.then()` و `.catch()` مصرف می‌کنید یا با `await`. `await` همان خط را متوقف می‌کند تا وعده به نتیجه برسد، بدون آنکه کل صفحه قفل شود.
- **`async/await`:** `await` فقط داخل تابعی که با `async` مشخص شده، یا در سطح ماژول، مجاز است. فایده‌اش این است که خواندن کد ناهمگام شبیه کد همگام می‌شود، از بالا به پایین. خطا را با `try/catch` می‌گیرید. بلوک `finally` چه موفقیت و چه شکست اجرا می‌شود و جای درستِ دوباره فعال کردن دکمه است.
- **`fetch` سه مرحله دارد:**
  1. `const response = await fetch(url)` درخواست را می‌فرستد و تا رسیدن پاسخ صبر می‌کند. `response` هنوز بدنهٔ خوانده‌شده نیست. اطلاعات وضعیت را دارد.
  2. `response.ok` را بررسی کنید. این ویژگی وقتی درست است که کد وضعیت بین ۲۰۰ و ۲۹۹ باشد. **`fetch` برای ۴۰۴ و ۵۰۰ خطا پرتاب نمی‌کند.** فقط وقتی درخواست اصلاً به سرور نرسد، مثلاً قطع اینترنت، خطای DNS، یا رد شدن به‌خاطر CORS، با `TypeError` رد می‌شود. CORS قاعده‌ای است که مرورگر با آن جلوی خواندن پاسخ یک مبدأ دیگر را می‌گیرد، مگر سرور اجازه داده باشد.
  3. `const data = await response.json()` بدنه را می‌خواند و به شیء جاوااسکریپت تبدیل می‌کند. اگر بدنه JSON معتبر نباشد، `SyntaxError` می‌گیرید. JSON شکل متنی داده است، با کلیدهای داخل نقل‌قول، که سرور و مرورگر هر دو می‌فهمند.
- **سه حالت رابط که همیشه باید طراحی شوند:** در حال بارگذاری، تا کاربر فکر نکند کلیک بی‌اثر بوده. خطا، با پیامی که کاربر می‌فهمد نه فقط یک خط در Console. نتیجهٔ خالی، وقتی درخواست موفق است ولی فهرستی برای نشان دادن نیست. این سه با هم فرق دارند و یک پیام واحد برای هر سه گمراه‌کننده است.
- **روش‌های HTTP:** `GET` داده را می‌خواند و نباید چیزی را در سرور عوض کند. `POST` منبع تازه می‌سازد. `PUT` یا `PATCH` منبع موجود را به‌روزرسانی می‌کنند. `PUT` معمولاً کل منبع را جایگزین می‌کند و `PATCH` فقط بخش تغییریافته را. `DELETE` منبع را حذف می‌کند. کدهای پرتکرار را با معنا بگویید: `200` موفق، `201` ساخته شد، `400` درخواست بد از سمت client، `401` هویت کاربر تأیید نشده، `404` منبع پیدا نشد، و `500` خطای داخلی سرور.
- **امنیت:** دادهٔ آمده از API را با `textContent` در صفحه بگذارید، نه با `innerHTML`، چون متن سرور ممکن است تگ داشته باشد و مرورگر آن را اجرا کند.

اشتباه‌هایی که خروجی قابل دیدن دارند:

- فراموش کردن `await` باعث می‌شود به‌جای داده، یک Promise روی صفحه به شکل `[object Promise]` دیده شود، چون شیء وعده به رشته تبدیل شده نه مقدار داخل آن.
- بررسی نکردن `response.ok` باعث می‌شود صفحهٔ ۴۰۴ را مثل موفقیت به `response.json()` بدهید و یا خطا بگیرید یا دادهٔ اشتباه نشان دهید.
- اگر خطا فقط در Console باشد، کاربر فقط صفحهٔ خالی می‌بیند. پیام را در خود صفحه بنویسید.
- اگر هنگام بارگذاری دکمه را `disabled` نکنید، چند کلیک پشت سر هم چند درخواست هم‌زمان می‌فرستد و پاسخ‌ها به ترتیب غیرمنتظره می‌رسند.
- `fetch` از صفحه‌ای که با `file://` باز شده به یک API روی `localhost` اغلب به‌خاطر محدودیت مبدأ مسدود می‌شود. برای این دمو صفحه را از راه یک سرور محلی باز کنید، یا از API عمومی همین جلسه استفاده کنید.

## Live Coding

در `live/app.js` مسیر را این‌طور نشان دهید: کلیک روی دکمه، نوشتن وضعیت «در حال بارگذاری» و غیرفعال شدن دکمه، سپس `fetch`، سپس بررسی `ok` و خالی نبودن فهرست، و در پایان نمایش پنج کاربر. برای دیدن حالت خطا، در DevTools از تب Network گزینهٔ Offline را روشن کنید، یا نشانی را به `/userss` تغییر دهید تا پاسخ ۴۰۴ بیاید. هر دو شکست را جدا نشان دهید، چون یکی خطای شبکه است و دیگری خطای HTTP.

## تمرین API

با نشانی `https://jsonplaceholder.typicode.com/posts?userId=1` پست‌های کاربر اول را نشان دهید. هر پست عنوان و متن دارد. بخش پرس‌وجو بعد از `?` یعنی «فقط پست‌هایی که userId آن‌ها ۱ است». سه حالت بارگذاری، خطا و فهرست خالی را هم در صفحه طراحی کنید.

## تکلیف

1. با کلیک روی هر کاربر، پست‌های همان کاربر از `/posts?userId=ID` بارگذاری شود. شناسه را از دادهٔ همان کاربر بردارید و در نشانی بگذارید، نه اینکه همیشه کاربر ۱ را بخوانید.
2. دکمهٔ «تلاش دوباره» فقط در حالت خطا دیده شود و همان درخواست آخر را تکرار کند. در حالت موفقیت این دکمه لازم نیست و باید پنهان باشد.
3. با `Promise.all` کاربران و پست‌ها را هم‌زمان بخواهید و تعداد پست هر کاربر را کنار نامش نشان دهید. `Promise.all` وقتی همهٔ وعده‌ها موفق شوند آرایهٔ نتیجه‌ها را می‌دهد و اگر یکی شکست بخورد کلش رد می‌شود، پس `try/catch` باید دور هر دو درخواست باشد.
